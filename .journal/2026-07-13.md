# 2026-07-13 — Fix `t.map is not a function` en apps-bundle.json (DHIS2 2.43) + tests de integración

## Resumen

Error en producción tras instalar la app: `Uncaught Error: t.map is not a function` en el arranque, dentro de `AppD2Repository.get()`. Causa raíz: `apps-bundle.json` cambió de formato entre DHIS2 2.42 y 2.43.

## Diagnóstico

Comparado contra instancias reales de `play.im.dhis2.org` (2.40, 2.41, 2.42, 2.43), autenticando con cookie de sesión (Basic Auth solo no basta, redirige a login):

- **DHIS2 <= 2.42**: `apps-bundle.json` devuelve un **array plano**, cada entrada con `webName` (nombre de carpeta real, ej. `dhis-web-data-visualizer`).
- **DHIS2 >= 2.43**: devuelve un **objeto** `{ buildDate, apps: [...] }`, y las entradas **ya no traen `webName`**, solo `name` (ej. `data-visualizer-app`).

El código hacía `response.map(...)` asumiendo siempre un array — con el objeto nuevo, rompía.

### Validación de la inferencia de `webName`

Comprobado empíricamente en 2.43: la regla `webName = "dhis-web-" + name.replace(/-app$/, "")` predice correctamente el `baseUrl` real de **29 de 29** apps del bundle que también están instaladas (la única excepción, `event-charts-app`, ya no existe con ese nombre en `/apps` de 2.43 — fue renombrada a `event-visualizer`, y no es una de las apps consumidas por el dashboard).

### Por qué `bundledApps` importa de verdad (no es solo teórico)

En **2.41** (instancia real), `maps` y `data-visualizer` **no aparecen en `/apps`** (solo `line-listing` sí) — únicamente están en el bundle. Este es el caso real que justifica mantener el fallback en vez de simplemente descartar apps sin `webName`.

### Dónde importa la lista combinada de apps

Solo dos consumidores en todo el código:
1. `useDhis2Url.ts` (`findAppByVisualization`) — resuelve `pluginLaunchUrl` de `maps`/`line-listing`/`data-visualizer` para el iframe del dashboard item.
2. `VisualizationContents.tsx` (`shouldUseAppRuntimePlugin`) — decide runtime plugin moderno vs iframe legacy según `version` de esa misma app.

Confirmado que el fix no fuerza caída a plugins legacy: la decisión depende solo de `installedApps` (con versión real del servidor), no del bundle.

## Solución aplicada

`src/data/repositories/AppD2Repository.ts`:
- Dos tipos separados sin interfaz común: `BundledD2AppLegacy` (2.40-2.42, con `webName`) y `BundledD2App` (2.43+, sin `webName`).
- Distinción por la **forma del JSON completo** (`Array.isArray(json)` vs `Array.isArray(json?.apps)`), no por presencia de un campo suelto.
- `buildBundledAppLegacy()` usa `webName` real; `buildBundledApp()` infiere `webName`/`key` desde `name`.
- `fetchBundledApps()` con `.catch(() => [])` — un bundle caído/404/redirigido a HTML de login ya no rompe la carga de apps, solo se queda sin ese fallback.
- Quitado un guard defensivo redundante sobre `installedApps` (`/apps` no cambió de forma entre 2.42 y 2.43, solo el bundle cambió).

## Tests de integración añadidos

`src/data/repositories/__tests__/AppD2Repository.spec.ts` — 5 tests con MSW interceptando red real (`/api/apps` + `/dhis-web-apps/apps-bundle.json`), patrón `givenA...`/`whenGettingApps` (mismo estilo que `uhcpw`). Cubre: installedApps con datos reales, bundle legacy, bundle nuevo con inferencia, precedencia de installedApps sobre bundledApps, resiliencia ante bundle caído.

### Infraestructura de test añadida
- `src/utils/MockWebServer.ts` — portado de `uhcpw`, pero migrado a **msw v2** (`http`/`HttpResponse` en vez de `rest`/`ctx`). msw v1 depende de `path-to-regexp@1.9.0` (CJS puro sin export `match`), que rompe bajo el resolvedor ESM estricto de Vite/Vitest — v1 solo funciona en proyectos con Jest+Babel (como `uhcpw`), no aquí.
- `package.json`: `msw@^2` añadido; resolution de `path-to-regexp` (fijada a `1.9.0` por un fix de seguridad previo para react-router) acotada por scope — `react-router-dom@**/path-to-regexp` y `react-router@**/path-to-regexp` — para no bloquear la `^6.3.0` que pide msw v2.

## Incidencias / lecciones

- **Node version**: el proyecto pide Node 20.19.4 (`.nvmrc`). Corriendo vitest con Node 18 (el que quedó activo en el shell), el proceso **se cuelga silenciosamente sin ningún error** al usar msw v2 — consume CPU indefinidamente sin logs. Hacer `nvm use` antes de correr tests en este repo es obligatorio, no opcional.
- `getMockApi()` (helper existente del proyecto, basado en `axios-mock-adapter`) no sirve para testear `D2Api` con `backend: "fetch"` — ya había un comentario en el código (`src/utils/tests.tsx`) documentando esto. Por eso hace falta MSW para tests de integración de repositorios.
- Todas las URLs de play.im.dhis2.org usadas se obtuvieron de `https://api.im.dhis2.org/instances/public` (la API que respalda `im.dhis2.org/public/instances`).
